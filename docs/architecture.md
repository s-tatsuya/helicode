# Architecture

Helicode is a re-implementation of Helix's editing model that uses VS Code
purely as a rendering and text-storage backend. Reading the Helix source
(`helix-core`, `helix-term`) side by side with `src/core` and `src/engine`
should feel familiar: function names and semantics are kept wherever possible.

```
src/
  core/        pure TypeScript, no VS Code dependency (unit tested)
    text.ts        TextDoc interface, char categories, graphemes, visual columns
    range.ts       Range / Selection (anchor, head, cursor, put_cursor, invariants)
    words.ts       word motions (movement.rs)
    paragraph.ts   paragraph motions
    textobjects.ts word / paragraph / pair textobjects
    surround.ts    pair discovery (surround.rs)
    brackets.ts    PAIRS table + plaintext bracket matching
    search.ts      regex helpers, select/split/keep on matches
    changes.ts     transactions and offset mapping
    increment.ts   number/date increment
    keys.ts        Helix key notation
    registers.ts   registers
  engine/
    keymap.ts      key trie, user overrides
    defaults.ts    default keymap (default.rs transcribed)
    engine.ts      modes, key dispatch, macros, jumplist, command registry
    editor-state.ts per-editor selection sync with VS Code, insert-mode anchors, decorations
    commands/      the commands, grouped like helix-term/src/commands
  vscode/
    document.ts    TextDoc adapter with line-start caching
    prompt.ts      regex/input prompts (QuickPick based)
    cmdline.ts     `:` commands
    labels.ts      gw jump labels
    statusbar.ts
  treesitter/
    index.ts       web-tree-sitter loader, incremental parsing, Syntax helper
    queries.ts     Helix `; inherits:` resolution
  extension.ts   activation, `type` interception, event wiring
```

## Selection model

A Helix `Range` is `{anchor, head}` over UTF-16 offsets, half open. The cursor
is the grapheme before `head` for forward ranges and at `head` for backward
ranges. `ensureInvariants` enforces the same invariants as
`Selection::ensure_invariants`: minimum width of one grapheme (except at EOF),
grapheme alignment, sorted and merged ranges.

Mapping to VS Code selections (`EditorState.toVscode`):

- a one-grapheme range becomes an *empty* VS Code selection at the cursor, so
  VS Code's block cursor draws exactly the Helix cursor;
- wider ranges become a real VS Code selection with the same anchor/active,
  plus a decoration on the cursor grapheme (primary and secondary colours) so
  the cursor position inside the selection stays visible like in Helix;
- VS Code's primary selection (`selections[0]`) is Helix's primary range.

The cursor style switches to a thin line while any range is wider than one
grapheme because VS Code would otherwise paint a block on the character *after*
a forward selection.

External selection changes (mouse, `gd`, undo) are converted back with
`fromVscode`; empty selections become one-grapheme ranges.

## Key dispatch

Printable keys arrive through the overridden `type` command; every other key is
declared in `package.json` (generated by `scripts/gen-keybindings.mjs`) and
forwarded to `helicode.key` with the Helix key name. `Engine.handleKey`
implements `helix-term`'s key handling:

1. pending `on_next_key` callbacks (`f`, `r`, `ms`, `mi`, `"`, `gw` ...);
2. insert-mode keymap (special keys only, characters go to `default:type`);
3. count digits (`0` only continues a count), `"` register selection;
4. key trie lookup with minor modes, sticky modes (`Z`, `Space G`) and Esc
   cancelling pending keys.

Commands receive a `CommandContext` (count, register, mode, editor state) and
are `async`; keys are queued so an awaiting command cannot interleave with the
next key.

## Insert mode

Helix keeps selections during insert mode and moves anchors with the text.
VS Code needs empty selections while typing, so `EditorState.beginInsert`
records the Helix anchors, sets empty VS Code cursors at the Helix cursor
positions and then tracks the anchors through every `onDidChangeTextDocument`
event (`mapOffset` with `Assoc.After`). `endInsert` rebuilds the ranges from
the tracked anchors and VS Code's cursors, applying `append_mode`'s
"restore cursor" rule. The result is that `i`/`a`/`c`/`o` + typing + `Esc`
leaves the same selection as Helix.

Typing itself is VS Code's own (`default:type`), so IME composition,
auto-closing pairs, snippets and suggestions behave normally. Typed text and
special keys are recorded for `.` (repeat last insert) and macros.

## Editing

Commands build a list of `Change`s in pre-edit offsets (like Helix's
`Transaction::change_by_selection`) and apply them with one `editor.edit`
call, then set the computed post-edit selection. `changeBySelection` mirrors
Helix's running-offset computation so multi-selection edits land exactly where
Helix would put them.

Undo relies on VS Code's undo stack. Edits that enter insert mode disable the
trailing undo stop so the following typing merges into the same step when
VS Code allows it.

## Tree-sitter

`web-tree-sitter` (WASM) is loaded from `wasm/web-tree-sitter.wasm`; grammars
come from `@vscode/tree-sitter-wasm` (compiled with a matching ABI). Trees are
parsed lazily on first use and kept up to date incrementally via `tree.edit`
from document change events. `Syntax` ports `match_brackets.rs` (fuzzy bracket
matching), `textobject_treesitter`, `goto_treesitter_object` and `object.rs`
(expand/shrink/siblings/children/parent edges). Queries are Helix's own
`textobjects.scm` files with `; inherits:` resolved; each is compiled against
the bundled grammar at build time (`npm run check-queries`).

## Notebooks

Notebook cells are ordinary text editors, so the whole engine works inside a
cell. The cell list receives a separate set of keybindings (see
`notebooks-and-webviews.md`).
